# 09: M2 close-out — the detection matrix, the guarantees, the dogfood proof

**What to build:** The evidence that Auto-Record works, on both platforms, measured rather than asserted. M1's close-out owed a WER number; this one owes false-negative and false-positive rates from real browsers.

**Blocked by:** 03, 04, 05, 06, 07, 08.

Status: closed but for two items the Operator owns — Arc and Edge (declined), and the Windows run (deferred). Every shipped Watchlist row is now observed live on macOS.

- [x] **Helper attribution is covered for all four, and fixing Safari's found a real defect.** With Safari open, this machine's audio process list holds `com.apple.WebKit.GPU` and never `com.apple.Safari` — so Safari could not have triggered a Browser Meeting at all, and no test said so because every test asked about the name Safari does not use. WebKit's children now resolve to Safari; Chrome, Edge and Arc resolve through the `.helper` rule.
- [x] **Chrome and Safari both observed live**, each triggering Browser Meetings on real hardware and auto-stopping when the microphone was released. Safari's run is the one that mattered: it exposed two defects that no test had — its audio processes identify as WebKit, and a failed start was being read as the Operator's Stop.
- [ ] **Arc and Edge: declined, not blocked — and the assumption under them is now checked as far as it can be without installing them.** The Operator was asked whether to install them for the matrix and chose not to (2026-08-28). That absence is a decision rather than an omission, but after Teams and Safari it is not something to leave resting on "it is unit-tested", since both of those were unit-tested too and both were dead.

  What the row actually assumes is that Arc and Edge name their helper processes `<bundle id>.helper`. That is now read off the shipped Chrome framework on this machine rather than assumed: Chromium builds `com.google.Chrome.helper` for the main and GPU helpers and `com.google.Chrome.helper.renderer` for renderers, and `com.google.Chrome.helper` is what was observed holding the microphone during a live trigger. The tests asserted `com.google.Chrome.helper.Renderer` — capital R, a string Chromium does not ship. It mapped correctly anyway, because the rule cuts at `.helper`, but asserting an invented id is the habit that cost us Teams, so the real ones are asserted now.

  So the extrapolation to Arc and Edge is within one architecture: they are Chromium builds of the same framework, and the helper id comes from Chromium's own build template, not a vendor choice. That is a materially different claim from the two that failed — Teams is not Chromium, and Safari is not Chromium. It is still not observation. **What no amount of reading can settle is whether their audio actually comes from a `.helper` process at all**, which is exactly what Teams got wrong: Teams has `.helper` processes and records from `.modulehost` instead. One `open -a Arc` on a page holding the microphone would answer it in a minute.

  Also noted while reading the framework: `com.google.Chrome.framework.AlertNotificationService` contains no `.helper` and so maps to itself. It is the notifications helper and does not hold a microphone, so it is not a defect — recorded because it is the same shape as the one that was.
- [x] **Every shipped row triggers a Meeting attributed to itself**, driven through the real Core — and every one of the three has now also been observed live. This line originally reasoned that a live run "would add only whether the platform reports *that application* holding the microphone". That was the whole risk, not a residue of it: it is exactly what Teams failed, and what Safari failed before it. Two of the four Watchlist rows shipped broken and passed every test, because a fixture cannot tell you the name an app uses when it records. Live observation is not confirmation of this criterion; it is the criterion.
- [x] **Zoom observed triggering on real hardware**: its microphone test took the device, Auto-Record started a Meeting attributed to `us.zoom.xos`, and quitting Zoom auto-stopped it.
- [x] **VooV observed triggering on real hardware**: its microphone test took the device, Auto-Record started a Meeting attributed to `com.tencent.tencentmeeting`, and quitting it auto-stopped. Both bundle ids were checked against the real installs and match what ships.
- [x] **Teams observed triggering on real hardware — and the run found the defect that the reasoning above had ruled out.** With the Operator signed in (2026-08-29), Teams' own Make-a-test-call took the microphone and Auto-Record did **nothing**. The process holding the microphone is `com.microsoft.teams2.modulehost`: no `.helper` in the name, so `responsible_app` left it alone and the shipped `com.microsoft.teams2` row never matched. Teams — one of the three named meeting apps ADR-0030 ships — could not have triggered on macOS at all. Mapped, and re-run against the same call: `Auto-Record started a Meeting app="com.microsoft.teams2"` in ~6 s, the echo bot's speech captured and transcribed correctly, and auto-stop at ~45 s when the call ended. The Meeting was deleted.
- [x] **Measured, on a small sample — and the sample is the thing to read carefully.** Four live trials against the real detector: three rounds of Chrome taking and releasing the microphone, and one round of an unwatched app holding it. **0 false negatives, 0 false positives.** Trigger latency 4–8 s; auto-stop consistently 20 s, which is the 15 s continuity window plus the release debounce and poll granularity — the design, arriving on time.

  That 0% false-negative rate is true and it is narrow, and saying only the number would mislead. It was measured on Chrome. Both real false negatives this milestone found — Safari, then Teams — were in apps outside that sample, and each was total: not a missed edge but an app that could never have triggered. Per-app, the honest figure before the fixes was **2 of 6 Watchlist rows dead on macOS**. All six are now observed triggering. The remaining exposure is the shape of the same bug in the two rows never run here (Arc, Edge) and on Windows, where nothing has been observed at all. Trigger latency and auto-stop timing are believable from the four trials; a detection *rate* needs a real day of use across apps, and this is not that
- [x] **The blocklist was tested against a real application that would otherwise match.** Chrome matches Browser Meetings; blocked, it stops triggering, and adding it to the Watchlist explicitly does not override that. A rule only ever tried against things nothing else matches has not been tested. Original criterion: the false-trigger blocklist: a dictation app, an IDE with a hot mic, and a screen recorder each observed **not** triggering
- [x] Guarantee tests extended rather than restarted — and they caught a real one: EventKit's default features linked **MapKit and CoreLocation**, now removed and forbidden by name. The zero-network test still passes. (Not yet run *with the calendar granted*, since this machine has no grant.)
- [x] The crash suite covers an auto-started Meeting: one is opened by the detector, the Core is dropped with it still running, and a new Core over the same History recovers the same Meeting: kill mid-recording, kill mid-stop, and confirm the auto-started Meeting recovers exactly as a manual one does
- [x] **The dogfood proof.** Chrome took the microphone on a localhost page; the live detector triggered Browser Meetings; Auto-Record started a Meeting attributed to `com.google.Chrome`; releasing the microphone ran the continuity window out and Auto-Record stopped it. 3m 20s, Mirror written, `Idle` again afterwards, and nobody pressed Record
- [x] **The compile half of the parity gate is green on both targets, locally.** `scripts/check.sh` now cross-builds and lints `x86_64-pc-windows-msvc` beside the macOS run.
- [x] **Both platforms are green in CI** (run 33230566682): `macos-14`, `windows-latest`, the Electron client and the ports ledger. CI had been red for at least three runs before this milestone, so the gate had never actually been met
