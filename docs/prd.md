## Problem Statement

People who live in meetings need a durable, searchable record of every conversation. Today they choose between polish and privacy. Cloud notetakers (Granola) deliver the polished record — summaries woven from the transcript and the user's own rough notes, searchable history — by putting every conversation on someone else's servers. Local notetakers keep the record home but hedge it: anarlog ships local diarization and cross-meeting voiceprints, yet surrounds them with thirty cloud ASR adapters, hosted routing, and cloud sync — local is a mode, not a guarantee; Meetily's free edition stays thin (no diarization, no auto-record, no CLI). And every local notetaker still puts a per-meeting act between the Operator and capture — a prompt to accept, a button to press — so the most painful missing transcript remains the meeting you forgot. Nobody offers the polished record — diarized, speaker-persistent across meetings, steered by the Operator's own notes, captured automatically — over storage that provably never leaves the machine.

## Solution

A desktop app for macOS and Windows, shipping v1 on both together (ADR-0025 as amended): a Notetaker that never misses a meeting. One Rust binary — the Core — runs at login and watches for a Watchlist meeting app (Zoom, Microsoft Teams, VooV, or any browser in a call) using the microphone; when one is, it starts recording by itself (Auto-Record, on by default). It live-transcribes on-device, shows live captions, and — post-meeting — diarizes into persistent Speakers, generates a Summary steered by the Operator's own Notes, and files everything into a searchable local History with Markdown mirrors. The Electron app and the CLI are thin Clients of the Core over a typed local protocol — capture never depends on a UI being open. Summary — the product's one LLM feature — is switchable between a local model and a BYO cloud API.

Two by-construction guarantees define the product:

1. **Closed Boundary** — History reaches the cloud through no code path. A cloud Backend can only ever receive the Current Meeting.
2. **Nothing Ambient (narrowed, ADR-0023/0036)** — beyond Meeting Detection (application and microphone *state*) and, when granted, the local calendar (schedule, titles, attendees — never via cloud calendar APIs), the app processes no input it wasn't explicitly handed: no screen content, no filesystem indexing, no contacts.

## User Stories

### Recording & transcription

1. As an Operator, I want manual record controls (menu-bar/tray control and global hotkey) alongside Auto-Record, so that I can capture conversations the Watchlist doesn't cover.
2. As an Operator, I want microphone and system audio captured together, so that both sides of the call are in the Transcript.
3. As an Operator, I want live captions while recording, so that I can confirm transcription works and glance back at what was just said.
4. As an Operator, I want a recording indicator visible at a glance — the Core's tray icon, revealed by mouse-to-top in fullscreen; a Core-native floating mini-indicator is evaluated in M5 — so that I am never recording without knowing it.
5. As an Operator, I want stopping the recording to immediately persist the Meeting, so that a crash after the call cannot lose the record.
6. As an Operator, I want transcription to run entirely on my machine with no configuration able to change that, so that raw meeting audio can never leave my device.
7. As a multilingual Operator, I want transcription that handles the languages my meetings actually happen in, including code-switching, so that the record is usable.

### Auto-Record

8. As an Operator, I want EverTranscript to start recording by itself when a Watchlist app is in a meeting (app active + microphone in use), so that no meeting is ever missed.
9. As an Operator, I want the watcher to launch at login, so that detection is already running at my first meeting of the day.
9b. As an Operator who granted calendar access, I want scheduled meetings pre-armed and announced — the Meeting born already carrying the event's title and attendees — while recording still waits for the real call, so that punctuality never depends on me and a skipped meeting records nothing; and if nothing triggers by ~2 minutes past the scheduled start, I want one follow-up notification offering manual record, so that phone and off-list meetings become recoverable instead of provable misses (ADR-0036).
9c. As an Operator, I want a visible launch-at-login toggle (default on, registration-only — disabling it states plainly that detection sleeps until I next open the app) and a separate tray Quit that stops the Core now, so that leaving the always-on posture is two legible acts that never conflate with the Auto-Record switch.
10. As an Operator, I want recording to stop by itself when the detected meeting ends, so that unattended capture never runs all day.
11. As an Operator, I want my manual Stop to win — detection must not restart recording for the rest of that meeting — so that the machine never overrules me.
12. As an Operator, I want recording to begin mid-meeting when detection comes online during one, so that a partial record beats no record.
13. As an Operator, I want to see and edit the Watchlist, so that I always know exactly what the app watches — and can extend it.
14. As an Operator, I want a single visible Auto-Record switch, so that turning the ambient behavior off (and back on) is one legible act.

### The Core & Clients

15. As an Operator, I want capture, transcription, and storage to live in the always-on Core with the UI as a separate process, so that closing — or crashing — the app window never kills a recording.
16. As an Operator, I want a CLI for control and query (daemon status, record start/stop, Auto-Record switch, launch-at-login toggle, Watchlist edits, History search, transcript export to stdout), so that my record is scriptable and pipeable.
17. As a Windows Operator, I want the same product with the same local-only guarantees shipping at the same time, so that my platform decides neither my privacy nor my wait (ADR-0025 as amended).

### The record

18. As an Operator, I want every Meeting in a local, full-text-searchable store, so that I can find any conversation ever had.
19. As an Operator, I want each Meeting auto-mirrored to a Markdown file in a folder I choose, so that my record is greppable, syncable, and usable without the app.
20. As an Operator, I want the record to be immutable — the app never rewrites what was said, so that my History is trustworthy evidence.
21. As an Operator, I want to delete a whole Meeting (including its audio) as a single legible act, so that removal is exact and complete — including recordings Auto-Record captured that I never wanted.
22. As an Operator, I want meeting audio kept by default, so that better future models can re-transcribe and re-diarize my History; and I want a global knob to not keep it.
23. As an Operator, I want the post-meeting title suggested from the Transcript to apply automatically — always mine to edit — so that my auto-captured History and its Mirror filenames aren't a list of "Untitled, 3pm".

### Notes

24. As an Operator, I want a markdown Notes pane I can jot into during the call, so that my own thoughts are captured next to the transcript.
25. As an Operator, I want Notes to stay editable forever (unlike the record), so that I can annotate past Meetings anytime.
26. As an Operator, I want the Summary to treat my Notes as its strongest signal of what mattered, so that rough jottings come back as clean, personal notes.

### Speakers & diarization

27. As an Operator, I want post-meeting Diarization to attribute the Transcript to Speakers, so that I know who said what.
28. As an Operator, I want every voice to resolve to a persistent Speaker across Meetings, so that "what did Alice say last month" works without ceremony.
29. As an Operator, I want naming a Speaker to retroactively label all their past appearances, so that one act organizes my whole History.
29b. As an Operator, I want to re-assign a mis-attributed segment to the right Speaker — my correction layering above the machine's attribution, never rewriting it — so that recognition errors are mine to fix and the machine learns from the fix (ADR-0009 as amended).
30. As an Operator, I want a Voice Registry listing every Speaker and Voiceprint the app holds, so that the biometric inventory is fully inspectable.
31. As an Operator, I want to delete any Speaker's Voiceprint, so that the app stops recognizing them without touching the record.
32. As an Operator honoring a Participant's deletion request, I want Voiceprint deletion plus Speaker rename to compose into de-identification, so that I can honor the request to the degree I choose.
33. As an Operator, I want Diarization to run only locally with no cloud form at all, so that voices are never a network question.
33b. As an Operator, I want both voices attributed when people talk over each other, and a two-word interjection attributed too, so that the record covers the whole meeting rather than only its tidy parts — the shipped pipeline gives overlap and sub-second speech no attribution at all, which is most of its measured error (ADR-0037).
33c. As an Operator, I want a Participant never recognized as a *different* Participant, so that a name in my History is never a false claim about someone — the one diarization failure that puts something untrue into a record ADR-0009 makes permanent.
33d. As an Operator with a two-hour meeting, I want Diarization to finish in minutes, so that meeting length is not a reason the record stays unattributed.
33e. As an Operator, I want an embedding-model change to keep every Speaker, name, and past attribution, re-process my History by itself, and relearn my named Speakers' Voiceprints from Kept Audio — visibly, pausing while I record, resuming after a quit, and stoppable — so that a better model never costs me recognition or the record (ADR-0037, ADR-0035 as amended).
33f. As an Operator, I want a Voiceprint I deleted to stay deleted through every future model change, so that deleting it was an act and not a pause — and so that what I told a Participant remains true (ADR-0009 as amended).
33g. As an Operator, I want naming a Speaker with a name my History already holds to join the two after I confirm, so that one Alice exists however many times her voice has come back as a new pseudonym.
33h. As an Operator recording alone on headphones, I want to be recognized as "You" without enrolling, never to be enrolled by a ten-second test recording, and never to end up with a second "You" in my Registry, so that the common case needs no ceremony and the Registry stays honest (ADR-0029 as amended).
33i. As a maintainer, I want Diarization's accuracy and cross-meeting recognition measured by a committed harness against named bars, so that the next change to this pipeline is judged rather than believed.

### Summary

34. As an Operator, I want a post-meeting Summary generated locally by default, so that ending a meeting never silently ships its transcript anywhere.
35. As an Operator, I want the Summary to end with extracted action items, so that follow-ups don't require re-reading.
36. As an Operator, I want enabling cloud Summary to require a hard one-time warning, so that the single biggest possible exfiltration is impossible to enable unknowingly.

### Backend & the Knob

37. As an Operator, I want a local/cloud Knob on Summary — the one LLM feature — so that its privacy/quality trade is mine to make.
38. As an Operator, I want cloud-Backend failures to auto-switch cloud→local only — never local→cloud — with a visible active-backend indicator, so that a network blip can't betray a privacy choice.
39. As an Operator, I want Strict Mode ("never auto-switch; tell me on failure"), so that I can trade resilience for absolute predictability.
40. As an Operator, I want curated cloud presets carrying verified data-handling labels (training, retention, ZDR), plus a fully open custom base-URL field, so that I'm informed but never gated.
41. As an Operator, I want API keys stored only in the OS credential store (macOS Keychain / Windows Credential Manager), so that secrets never appear in the database, mirrors, or logs.
42. As an Operator, I want Summary's system prompt exposed as an editable field with reset-to-default, so that I can shape my notes without waiting for a feature.

### Onboarding & trust

43. As a new Operator, I want a blunt one-time Briefing on recording consent law, voice profiling, and the fact that Auto-Record is on unless I turn it off, ending in an explicit acknowledgment — and nothing captured before that acknowledgment — so that I understand my obligations before the machine acts.
44. As a new Operator, I want linear setup where every requirement (permissions, model download, API key) is explained at the moment it's demanded, so that I exit setup fully armed and am never configuration-prompted at runtime again.
45. As a new Operator, I want the Summary Backend choice made explicitly by me (Local badged "Recommended", never preselected), so that runtime configuration traces to my own act.
46. As a privacy-conscious evaluator, I want the two guarantees stated in plain language and verifiable — the source open to read, entitlements on macOS, and a wire that speaks only enumerable Sanctioned Traffic — so that I can check the claims before trusting the product.
47. As an Operator, I want certainty that the app never indexes my filesystem or contacts, never reads screen content, and reads my calendar only if I granted it, so that "what does it know?" always has the answer "exactly what I gave it, plus which meeting app is running — plus, if I allowed it, my calendar's schedule and titles."

### Distribution

48. As an Operator, I want a signed direct download (Homebrew cask on macOS, winget on Windows) with in-app updates, so that installing and updating never depends on an app store's review of system-audio capture.

## Implementation Decisions

- **Platform & architecture:** Electron UI; all logic and the CLI in Rust (ADR-0025). One Rust binary — the Core — runs as an always-on daemon (the login item) owning detection, capture, ASR, Diarization, and storage, and doubles as the CLI via subcommands (binary `evertranscript`; `evt` documented as the suggested alias); the Electron app is a thin Client over a typed local IPC protocol — the codex app-server blueprint (ADR-0028): JSON-RPC-shaped JSONL over a unix socket (macOS) / named pipe (Windows), per-connection initialize with capability gating, a macro-defined protocol crate with ts-rs + schemars codegen, Meeting-scoped vs broadcast notification fanout, snapshot-then-tail on attach, and a lossy caption-delta subscription. The Core is the record's only writer (ADR-0026), owns the always-visible tray (recording indicator + record/stop controls; clicking opens the Client), and never auto-launches the Client — Auto-Record surfaces a system notification instead. Launch-at-login is a visible Settings toggle and CLI subcommand (`evertranscript autostart on|off`), default on and registration-only: a running Core stops only via the tray's explicit Quit (story 9c). Client stack: React 19 + Vite + Tailwind, strict TypeScript, protocol types from the generated ts-rs bindings, minimal state, no meta-framework. Repo layout: one Cargo workspace — `crates/evertranscript-core`, `crates/evertranscript-protocol`, `crates/evertranscript` (the binary; the Summary sidecar crate joins later) — with `clients/electron` (pnpm) beside it. Targets: macOS 14.4+ Apple Silicon and Windows 10+ x64, simultaneous v1 (ADR-0025 as amended; ADR-0027): one cross-platform Core with platform traits for capture, detection, autostart, credentials; CI builds and tests both from M1; every milestone closes on both platforms, and v1 ships only when detection works on Windows.
- **Capture (platform trait):** macOS — CoreAudio process taps + private aggregate device for system audio (ADR-0027) + cpal for microphone; Windows — WASAPI loopback + capture. Dual-channel end-to-end, with DTLN-shape AEC (via ort, system channel as echo reference) on the mic channel from M1 (ADR-0029). Churn/continuity per ADR-0029 as amended: absolute capture timestamps on one shared clock; independent mic hot-swap and system-audio self-heal with the session surviving both; ASR death never stops capture. Recording starts by explicit Operator action or by Auto-Record (ADR-0023); it never starts before the Briefing acknowledgment.
- **Detection (platform trait):** macOS — NSWorkspace running-app observation for process entries (Zoom, Teams, VooV incl. 腾讯会议) plus per-process microphone attribution via CoreAudio, which serves both the AND-mic condition and the Browser Meetings entry (any browser with a hot mic, helper processes mapped to the responsible app — ADR-0030); no window titles, no content. Optional precision naming (Settings, off by default): a Screen Recording grant restores per-site browser labels. Windows — Win32 process/window enumeration and audio-session mic state, no permission grant required; per-process attribution is v1 Windows work in M2 (anarlog's is a stub; Granola's `mic_monitor_v2` — mined from the shared JS bundle — is the shipped prior art). Calendar (ADR-0036, when granted): the EventKit local store on macOS (WinRT appointment store on Windows, M2) pre-arms detection at scheduled start, posts the heads-up, pre-creates the Meeting with the event's title and attendees, and feeds scheduled-end into the auto-stop window — capture still starts only on the trigger. A calendar-armed Meeting with no trigger by ~2 minutes past start prompts once ("'<title>' seems to be happening — nothing is recording"); ignored, the pre-created Meeting is discarded. Watchlist membership AND mic activity are both required to trigger (ADR-0024). Detection latches once triggered: a Meet tab moved to the background mid-call keeps recording while the mic stays hot. Launch-at-login via SMAppService / registry Run key; auto-stop after a ~15s continuity window, so device churn (a Bluetooth swap mid-call) never splits a Meeting; a manual Stop suppresses re-trigger for the remainder of that meeting (ADR-0023 as amended). No pre-trigger buffering exists in any form — recording begins at the trigger (ADR-0024 as amended).
- **ASR:** whisper.cpp via whisper-rs (ADR-0014 as amended by 0025 — the binding Meetily and anarlog both ship in production). Shipped default model: large-v3-turbo q8_0 (~870MB — the multilingual/Chinese quality the record deserves), smaller models selectable in Settings. The meeting-grade streaming layer (VAD + sliding-window chunking) is built in-house. GPU per platform: Metal on macOS, Vulkan/CUDA on Windows. ASR and Diarization are Anchors — permanently local, no Knob (ADR-0002).
- **Diarization:** post-meeting, local, channel-aware on both channels (ADR-0029 as amended). Produces per-segment Speaker attribution and voice embeddings; every voice clusters to a persistent Speaker with a stored Voiceprint (ADR-0008). Transcript segments reference Speaker records; display names are a live join, so renames propagate retroactively (ADR-0009). Naming a Speaker also confirms its Voiceprint (higher-trust matching thereafter), and naming one with a name History already holds **joins** the two after the Client confirms — named-into-named is refused; Operator mis-attribution corrections are appended hints that feed exemplars (ADR-0008/0009 as amended). **Reworked 2026-09-15 on the M3 close-out's measurement (ADR-0037):** M3 shipped 49.7% DER on AMI's test set where pyannote publishes 18.8% with the same two models, and an oracle that clusters perfectly still scored 32.6% — the turns were wrong before any model was consulted, because segmentation was reduced to a per-frame speaker *count* and the rules for choosing what a Voiceprint is built from were deciding who was talking. The pipeline becomes the **pyannote community-1 recipe both shipped local competitors run**: 10 s segmentation windows slid at **1 s** (today they do not overlap at all), one embedding per local speaker per window from masked audio, cross-window identity stitched rather than discarded, and per-speaker reconstruction in which overlap yields a turn for everyone in it and nothing is dropped for being short. The 1.5 s minimum and middle-10 s clip stay, scoped to picking embeddable material. Clustering becomes two-stage (blocks, then block centroids), replacing a cubic pass that spends ~15 minutes on a two-hour meeting. **One embedding does both jobs and it is ReDimNet2-B3** (PalabraAI, MIT, 192-d, raw 16 kHz waveform in with the mel frontend inside the graph — so no Rust fbank on that path), replacing WeSpeaker ResNet34-LM for clustering *and* Voiceprints, with plain agglomerative clustering and no PLDA. Granola splits the two across a masked WeSpeaker export and ReDimNet2-B3; the masked half needs a speaker-mask ONNX input nobody publishes, so either design ships an export of our own and this one ships one instead of two. The measured reason: across real meetings of the same colleagues, WeSpeaker puts 15–44% of *different*-colleague pairs above the match floor and both ReDimNets put none. Thresholds (merge, floor, margin) are re-derived on AMI dev and reported on test; until then the shipped 0.62/0.08/0.60 stand as named placeholders, not settled values. **A model change is an event the product handles:** a versioned migration clears every Voiceprint and exemplar while keeping every Speaker, name, `is_operator` flag, attribution, and correction; seeding then filters by the current model as a standing guard (today nothing anywhere compares an embedding's model before using it, and a 256-d/192-d cosine scores 0, so recognition would silently stop). A bulk re-run walks History oldest first, relearning each **named, unforgotten** Speaker from its own attributed segments — corrections winning, negatives rebuilt from corrections that took a segment away — while pseudonymous Speakers are re-minted and renumbered, and a Meeting with no Kept Audio keeps the attributions it has. Deleting a Voiceprint now also marks the Speaker **forgotten**, which is what lets the re-run tell a deliberate deletion from a cleared vector. Batch diarization becomes **one persistent queue** — a just-ended Meeting or an Operator request at the front, bulk work at the back, only a Meeting already in line refused — replacing M3's reject-don't-queue, whose refusal is invisible to the caller and clobbers the running job's status. The Operator is identified by three rules in order (ADR-0029 as amended): isolated mic (headphones the only playing output, mic not swapped) makes every mic-channel cluster the Operator without any act; else dominance at 80% of mic time with the margin and at least 20 s of that voice; else a Voiceprint match, gated on the Meeting holding 30 s of diarized speech and two speakers, below which that Voiceprint is withheld from the whole resolve. One flagged row forever — a bootstrap re-attaches rather than minting a second "You", closing a defect reachable today by deleting the Operator's Voiceprint and re-running one Meeting.
- **Models:** downloaded at first need with pinned checksums — Hugging Face primary plus an Operator-configurable mirror URL (ModelScope serves China); covers Whisper ggml, the Diarization ONNX pair, the AEC ONNX, and (Local Summary only) the sidecar's GGUF. Every entry records licence and source. **One model is the product's own export (ADR-0037):** neither ReDimNet2 nor ReDimNet publishes an ONNX, so the diarization embedding is exported by a committed, pinned script and published to Hugging Face like every other Provisioned Model — same host, so Sanctioned Traffic is unchanged (ADR-0034). Publishing is an outward-facing act taken once per model under a written decision, never a side effect of a build, and the registry entry is written when the pipeline first uses the model so no shipped build pins a URL still expected to move. Registry entries gain the model *version* the record already stores beside every Voiceprint, which is what makes a model change detectable at all.
- **Storage:** SQLite with FTS as source of truth, accessed via rusqlite on a dedicated writer thread — the single-writer rule made executable — with embedded migrations; per-Meeting Markdown Mirrors are regenerable projections, never independently edited (ADR-0005, 0009). Meeting ids are UUIDv7; Mirror filenames are `YYYY-MM-DD-<slug>-<id8>.md` — born with the detected app as the slug, renamed once when the Title lands (suggestions auto-apply, Operator-editable; native characters kept in slugs), with a marker (the first 12 hex of the id) as the durable handle the dirty-queue uses to rename and GC stale names; outside references should key on it, since retitles rename the file. **Twelve, not eight**: UUIDv7 opens with a 48-bit millisecond clock, so eight hex characters change only every ~65 seconds — every Meeting started inside one such window shared an audio filename, and the earlier one's audio was destroyed (found 2026-09-05 by recording two back-to-back). Voiceprint vectors are BLOB columns in the same database — the History folder is the complete portable unit, record and recognition together, plaintext at rest (FileVault/BitLocker is the disk story; ADR-0035). Default location `~/Documents/EverTranscript` (Windows: `Documents\EverTranscript`), Operator-relocatable: Mirrors at the top level, DB + audio in a hidden `.data/` subfolder (Windows adds the hidden attribute; the Core flags Mirrors-without-`.data` as an incomplete copy); models, caches, and logs stay in Application Support. Onboarding's folder step states the iCloud Desktop-&-Documents sync implication (ADR-0035 as amended). Mirror composition: YAML frontmatter (id, date, app, duration, speakers) → Title → Summary → Notes → Transcript (ADR-0005 as amended). Audio persists by default as one stereo MP3 per Meeting — mic left, system right, coded as independent channels so the split survives storage — encoded in the Core's own process as capture runs, so a crash leaves a file playable to its last frame, with a global keep-audio knob (ADR-0019, 0029, 0032 as reversed 2026-09-05). Notes are a first-class mutable entity; the record — Transcript text and the machine's attribution — is immutable, with Operator corrections layering above it as appended hints (ADR-0009 as amended); whole-Meeting deletion and Voiceprint deletion are the only destructive operations (ADR-0009, 0018).
- **LLM plumbing:** one OpenAI-compatible chat-completions abstraction serves Summary, the sole LLM feature; its one generation pass returns a fixed output contract — title suggestion, Summary body, action items — so story 23's title rides the sole feature (the pre-Summary default title is the overlapping calendar event's title when granted, else date + detected app); local backends and cloud presets are the same interface with different base URLs. The shipped local default is a bundled llama.cpp sidecar — Core-supervised, JSON over stdio, spawn-on-demand with idle timeout (ADR-0031) — with an installed Ollama/LM Studio **offered in the picker** like any other preset (auto-detect-and-prefer was withdrawn 2026-09-05: it would silently change which model summarises a Meeting, and the presets already reach a local server by base URL); Apple Foundation Models is a post-v1 opportunistic tier. Keys only in the OS credential store via a `keyring`-style abstraction (Keychain / Credential Manager). A small local model is the default Backend and the Fallback target.
- **Knob semantics:** Backend selection exists on Summary only; Fallback is cloud→local only with a required active-backend indicator; Strict Mode disables Fallback (ADR-0002, 0003). A cloud Backend receives at most the Current Meeting — the Closed Boundary is the absence of any other path, not a filter (ADR-0001).
- **Onboarding:** Briefing (consent + voice-profiling — stating that copies of the History folder carry voice data (ADR-0035) — + Auto-Record and calendar disclosure (ADR-0036), explicit acknowledgment) → permissions (macOS: microphone + system-audio recording; Windows: none; both platforms: a skippable, Recommended calendar grant — ADR-0036) and model downloads (Whisper, Diarization + AEC ONNX) → explicit Summary-Backend choice (Local recommended, never preselected) → that choice's remaining requirements. Configuration never prompts at runtime; unconfigured features show a legible state (ADR-0011, 0013). Auto-Record ships On; the Briefing states it bluntly (ADR-0023).
- **Localization:** UI strings externalized from M1; v1 ships English + Simplified Chinese at the public M2 moment. The Briefing's legal copy is per-jurisdiction counsel work, not mere translation.
- **Milestones:** M1 walking skeleton — Core daemon + ADR-0028 protocol end-to-end (manual record → dual-channel capture with AEC → live captions → SQLite + incremental AAC → mirror), the Core-owned tray, minimal Electron Client, CLI record/search; M2 Auto-Record (Watchlist watcher, login item, auto start/stop, suppression, calendar arming + event titles — ADR-0036); M3 Diarization + Speakers/Registry; M4 provider abstraction + the Summary Knob (keyring, Strict Mode, Fallback) proven end-to-end on Summary; M5 onboarding + polish (incl. evaluating the Core-native floating recording indicator) — every milestone closing on both platforms; Windows trait work rides the spine: WASAPI capture + named pipe (M1), Win32 detection + mic attribution + appointment store (M2), Credential Manager (M4), signed installer + winget (M5) (ADR-0015/0025 as amended).
- **Distribution:** macOS — Developer ID, notarized, direct download + Homebrew cask; Windows — signed installer, direct download + winget; electron-updater for both (it covers the bundled Core, ffmpeg, and the llama sidecar). No app stores (ADR-0016 as amended).
- **Posture:** open source, Apache-2.0, repo public at M2 dogfood quality; monetization deliberately deferred (ADR-0033). No telemetry or crash-reporting SDKs — crashes write local reports with manual export; the wire speaks only Sanctioned Traffic: the disableable update check, checksummed model downloads, and the Operator-chosen cloud Summary Backend (ADR-0034).

## Testing Decisions

- **Philosophy:** test external behavior only — observable outputs are SQLite content, mirror files, protocol responses/events as seen by Clients, and the exact bytes sent to LLM endpoints. No mocking of storage, diarization models, or the ASR engine in the default suite. Harness is Rust (`cargo test`); the Electron Client stays thin enough that the protocol contract, not a GUI rig, is the tested surface in v1.
- **Four seams**, each a trait boundary in the Core (the original two were user-approved; DetectionSource was added with Auto-Record, Diarizer with M3 — and the fourth is where the whole of ADR-0037's policy is tested, since seeding, joining, forgetting, re-minting, the Operator's three rules, and what a re-run replaces are all decidable with no models, no audio, and no GPU; its fixture must be able to produce overlapping turns and sub-second turns, which the recipe it replaces could not):
  1. **AudioSource** — live capture and fixture WAV/PCM playback are interchangeable at one point. End-to-end tests feed fixture meeting audio through the real whisper.cpp → store → Diarization → mirror → Summary pipeline and assert on the artifacts (transcript rows exist, Speakers cluster consistently across two fixture meetings sharing a voice, mirrors regenerate on rename).
  2. **LLM Backend endpoint** — tests point the Summary Knob at a local fake OpenAI-compatible server. This seam doubles as the **Closed Boundary sentinel**: the fake "cloud" asserts no request body ever contains History content (seeded canary strings from prior fixture Meetings must never appear). Killing the fake mid-generation exercises Fallback (switches to local, indicator state observable) and Strict Mode (no switch, failure surfaced).
  3. **DetectionSource** — the watcher consumes an injectable stream of app/mic state events. Fixture event sequences drive the Auto-Record contract end-to-end: Watchlist app + mic → recording starts; mic released past the continuity window → recording stops and the Meeting persists; release-and-rehot inside the window → one continuous Meeting; manual Stop → no re-trigger for that meeting; off-list app + mic → nothing.
  4. **Diarizer** — a finished Meeting's two channels in, turns plus per-cluster embeddings out, with a live ONNX implementation and a fixture one. Every attribution, persistence, naming, and re-run test drives the fixture; the ONNX path is tested for what only it can be.
- **Diarization is measured against named bars by a committed harness, and the measurement gates the merge (ADR-0037).** M3 owed a DER, produced one through a scratch harness, and deleted it — so the 49.7% and the embedding bake-off behind this rework are currently unreproducible, which makes the harness the first piece of work and the one with no useful ordering alternative. It takes audio plus a reference, drives the *shipped* pipeline rather than a copy, and reports **DER ≤ 18.8% on AMI's test set** and **cross-meeting EER ≤ 1% with no different-colleague pair above the match floor**. Neither number is a score to report afterwards; measuring after shipping is exactly the M3 shape this rework exists to correct. The migration is tested at the store over a file-backed database, because the claim is about what the next Core opens rather than about in-memory state; the re-run is tested through the protocol, because progress, pause, resume, and cancel are what a Client observes.
- **Guarantee tests are the crown jewels:** the Closed Boundary sentinel above; a Nothing Ambient audit asserting the macOS binary's entitlement/permission set stays exactly (microphone, system-audio recording — detection rides on these, adding none; Screen Recording appears only with opt-in precision naming (ADR-0030), Calendars only with the granted calendar step (ADR-0036)) and, on both platforms, that traffic never exceeds Sanctioned Traffic — none of it carrying meeting content — and that an all-local configuration with updates off produces literally zero network traffic; an artifact scan asserting key material never appears in SQLite, mirrors, or logs, and that no analytics or crash-reporting SDK exists in the binary (ADR-0034). The zero-network guarantee must hold with the reworked pipeline running, on the path where the models are present and actually execute — it skips loudly rather than quietly when they are absent, and asserts they were staged, so a model-less pass can never be mistaken for proof.
- **Framework & prior art:** greenfield — the fixture-audio library, the detection-event fixtures, and the fake endpoint server are built in M1/M2/M4 respectively and become the shared harness for everything after.

## Out of Scope

- Removed from scope by decision (ADR-0022): in-call assistance of any kind — teleprompter/suggestion feeds, in-meeting chat, stealth/capture-invisible overlays — and the assistant Corpus/retrieval stack that served it. This product is a notetaker, not a meeting copilot.
- Ratified non-goals (ADR-0021): mobile apps, team spaces/sharing/roles, coaching analytics, CRM/task-manager push, PDF/DOCX export (the mirror is the export), summary-template library, auto-JOINING meetings (detection observes; it never joins, bots, or acts outward), external audio import.
- Out of scope for the Diarization rework (ADR-0037): PLDA and VBx, unless the harness shows plain agglomerative clustering missing the bar; the masked-WeSpeaker half of Granola's two-model split, and with it any second export; a pure-Rust mel frontend, unnecessary once the export proved to carry no STFT node; far-field accuracy, since AMI Mix-Headset is close-talking and a microphone across a room is worse; and a separate Registry merge control, because the join arrives through naming, which is the same code behind one control instead of two.
- In-app audio playback is a non-goal (decided 2026-08-27): kept audio is reachable as a file — each Mirror's frontmatter carries its audio path into `.data/audio/` — and any player serves; revisit if dogfooding demands.
- Platform non-goals: Linux (a post-v1 question at best); Mac App Store and Microsoft Store (ADR-0016); CLI–GUI parity — the CLI stays control + query (ADR-0026).
- Post-v1 by decision: the Enhance family (Operator-invoked re-transcription/re-diarization, unlocked by kept audio); prompt-on-unknown-mic-use as a Watchlist complement (ADR-0024); a browser extension for precise browser-meeting metadata (ADR-0030); an MCP-server CLI subcommand speaking to the Core as a Client (anarlog precedent); Apple Foundation Models as an opportunistic Summary tier (ADR-0031); monetization, deliberately deferred (ADR-0033).
- Foreclosed permanently: ambient screen-content awareness, redaction/bridge mechanisms of any kind, and cloud calendar APIs (ADR-0001, 0020 as amended by 0023/0036 — the local calendar store is the one sanctioned calendar surface).

## Further Notes

- Top risks from the accumulated register: **detection reliability is product-defining** — a false negative is a broken headline promise. The fragile edge moved with ADR-0030: browser meetings ride per-process mic attribution (helper-process→responsible-app mapping, which M2's test matrix must prove across Chrome/Safari/Arc/Edge — both platforms in v1); the costs are coarse labels ("Chrome" until the post-meeting title suggestion lands) and non-meeting browser voice apps triggering — the mic-continuity latch, the removable Watchlist row, and whole-Meeting delete are the mitigations. **Counsel review of default-on Auto-Record against all-party-consent law before v1 ships** (mandatory, not a design task — now also covering the calendar disclosure, ADR-0036). **The protocol is load-bearing** — every feature crosses it; ADR-0028 answers the day-one versioning demand (per-connection initialize capabilities + experimental gating; keep changes additive). **The simultaneous-Windows scope is the accepted trap** (ADR-0025 as amended): two capture stacks, two signing pipelines, two QA matrices inside v1 — taken eyes-open with the named mitigations (CI builds both targets from M1, mined prior art for every Windows trait, and the anarlog clause: Windows detection parity is the ship gate). The scope trap ("thin" must be brutally enforced per milestone). whisper.cpp streaming quality on the Operator's real meeting languages is unverified homework (the cited prior art is dictation-shaped, not meeting-shaped). GPU contention is bounded — the local Summary model runs post-meeting, so it contends with live transcription only if a Summary is still generating when the next recording starts; profile in M4.
- **Diarization's rework carries two costs worth stating plainly.** Pseudonymous Speakers are renumbered by the model change, so an Operator who has been calling someone "Speaker 3" finds a different number after the upgrade; it was accepted explicitly and belongs in whatever the upgrade shows. And a named Speaker whose every Meeting has lost its Kept Audio ends with no Voiceprint at all — the Registry states the reason rather than leaving an empty row unexplained. The bulk re-run is the first thing in this product that touches all of History at once, which is why it pauses for recording, resumes across restarts, and is cancellable rather than merely visible.
- The usual anti-Electron objection (resident footprint) is answered by the architecture, not denied: the thing that lives at login is the Rust Core; the Electron Client runs only when opened (ADR-0026).
- Auto-Record raises recording volume by an order of magnitude (every standup, every huddle): post-meeting title suggestions (story 23) and whole-Meeting delete (story 21) are the triage tools; ADR-0019's keep-audio default stands — disk cost stays trivial at this volume at a speech-appropriate bitrate — but the figure once recorded here, 20–30MB/hr, was measured wrong: the AAC-192k actually implemented runs 86MB/hr (a 69.4h recording occupying 6.0 GB), and stereo MP3 reaches the original budget only at 64k. ADR-0032 carries the arithmetic and leaves the bitrate open.
