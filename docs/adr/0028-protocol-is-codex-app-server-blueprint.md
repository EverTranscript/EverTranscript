# The Core protocol is the codex app-server blueprint, with two deviations

> **Amended 2026-08-27 (consumption posture):** codex is consumed **read-and-port with attribution, never linked** — not from a registry (the workspace is unpublished, version 0.0.0 throughout), not as a git dependency, and not as a local-clone path dependency: its narrowest useful crate (`app-server-transport`) hard-depends on `codex-core` and closes over 1,045 of the workspace's 1,239 locked packages, while the code worth taking totals ~500 lines (unix-socket lifecycle, JSONL framing, RPC envelope, the codegen structure). Ported files keep their Apache-2.0 headers and arrive with a repo NOTICE file (created with the first ported file; both projects are Apache-2.0). A local clone built on a dev machine is welcome as a **reference rig** — run their daemon, probe the wire, diff generated schemas against ours — never as a build input.

ADR-0026's "typed local protocol" is concretized against openai/codex's app-server stack (verified against source 2026-08-27), which already ships our target shape — one server core reached by 0..N concurrent clients over a local socket, with work continuing at zero clients. Adopted wholesale: JSON-RPC-2.0-shaped messages over **newline-delimited JSON**; unix socket (0600) on macOS and named pipe on Windows; startup lock file, stale-socket cleanup, single-instance enforcement; a `protocol` crate with macro-defined request/response/notification tables and **ts-rs + schemars codegen** (TypeScript bindings for the Electron Client, JSON-schema fixtures committed and test-enforced); a per-connection `initialize` handshake (clientInfo, capabilities, experimental-API gating) as the additive-evolution mechanism; Meeting-scoped vs broadcast notification fanout with per-connection subscriptions; and **snapshot-then-tail** on attach — a Client connecting mid-recording gets the current Meeting state and transcript-so-far, then live deltas.

Two deliberate deviations, both where our clients and workload differ from codex's: (1) **named pipe, not AF_UNIX, on Windows** — the GUI client is Node/Electron, and libuv has no AF_UNIX on Windows while speaking named pipes natively; codex's WebSocket-over-UDS handshake is dropped for the same reason (an on-machine Node client gains nothing from it). (2) **Caption deltas are an opt-in, lossy/conflating subscription** — codex disconnects slow clients when queues fill, which suits interactive traffic; here a slow reader must get degraded captions, never a killed connection, and capture must never block on client consumption.

## Consequences

- codex remains the reference implementation for questions the blueprint leaves open.
- codex's daemon-lifecycle affordances are Unix-only; the Windows fast-follow owns that gap.
- The Core owns supervision-independent framing: launchd/SMAppService (macOS) and the Run key (Windows) start it; the codex pidfile daemonizer is unnecessary under a supervisor.
